# NET 대기 영상

대기·추첨 영상은 하나의 `MachineFrame` 안에 계속 마운트하며 표시 레이어만 교체합니다. 모두 9:16, `object-fit: contain`, 중앙 정렬입니다. 크롭을 사용하지 않아 데스크톱·가로 화면에는 여백이 생깁니다. 투명 버튼은 같은 프레임의 실제 표시 크기로 계산합니다.

## 리소스

| 역할 | 실제 경로 | 내용 |
| --- | --- | --- |
| 대기 영상 | `frontend/src/assets/gacha-idle.mp4` | 720×1280, H.264 Main/yuv420p, 30fps, 약 7.33초, 약 1.3MB, 오디오 없음 |
| 대기 포스터 | `frontend/src/assets/gacha-idle-poster.webp` | 편집한 대기 영상의 첫 프레임, 약 54KB |
| 기존 추첨 영상 | `frontend/src/assets/gacha.mp4` | 기존 파일 그대로 사용. 논리적으로 `gacha-draw.mp4` 역할 |
| 기존 추첨 포스터 | `frontend/src/assets/gacha-poster.jpg` | 추첨 로딩·재생 실패·복구 결과의 정적 배경 |

제공된 `Animate_gashapon_machine_capsule…_ac9055dc.mp4` 원본은 수정하지 않았습니다. 첫·끝 프레임의 머신 각도가 달라 마지막 0.6초를 첫 0.6초에 디졸브하고, 시작점을 0.6초로 옮겨 반복 경계를 연결했습니다. 디졸브 중 약한 이중 윤곽은 남을 수 있습니다. 90×160 RGB 축소 프레임으로 비교한 첫·끝 평균 절대 차이는 원본 24.36에서 편집본 5.76으로 줄었습니다. 이 수치는 완전한 시각적 일치를 의미하지 않습니다.

대기 영상과 추첨 영상은 구도·각도·장식이 다릅니다. 동일 컨테이너로 크기와 위치는 유지하지만 2D 확대·이동만으로 3D 원근을 완전히 맞출 수 없습니다. 두 영상 사이에 임의의 크로스페이드를 넣지 않았습니다. 완전히 이어지는 연출이 필요하면 기존 추첨 영상 첫 프레임과 같은 카메라·바닥 위치·머신 크기로 대기 영상을 다시 내보내는 것이 정확합니다. 현재 투명 터치 영역은 대기 영상의 손잡이와 보관통 이동 범위를 포함합니다.

## 상태와 재생

기존 상태 이름과 API는 유지합니다. 명세의 `DRAW`는 내부 `PLAYING`, `RESULT`는 내부 `REVEAL`에 해당합니다.

- `IDLE`/`REQUESTING`: 대기 영상 표시. API 실패 시 추첨 영상으로 넘어가지 않습니다.
- `PLAYING`: 대기 영상 숨김·정지, 기존 추첨 영상을 0초부터 재생. 머신 버튼 비활성화 및 기존 모달로 외부 입력 차단.
- `REVEAL`: 대기 영상 정지, 추첨 영상의 마지막 프레임과 기존 티켓 표시. 영상 없이 복구한 결과는 추첨 포스터를 사용합니다.
- 티켓 닫기: 기존 `reset()`으로 `IDLE` 복귀·대기 재생. 질문 등록창도 열려 있는 동안은 대기를 정지하고 닫힌 뒤 재개합니다.
- 문서가 숨겨지면 대기 정지, 다시 보이면 현재 상태가 대기일 때만 재생합니다. 늦게 처리된 `play()` 응답과 StrictMode 재연결도 고려합니다.
- 대기는 `autoplay`, `muted`, `loop`, `playsInline`, `preload="auto"`, `pointer-events: none`을 사용합니다. 재생 거절·로드 오류 시 영상을 제거하고 포스터와 터치 영역을 유지합니다. `prefers-reduced-motion`에서도 포스터를 사용합니다.

대기 영상은 한 번 받은 리소스를 브라우저 캐시로 반복 재생합니다. 데이터 절약/2G에서는 대기 다운로드를 생략합니다. 추첨 영상은 회선 미확인 시 `metadata`, 명시적 Wi-Fi/이더넷이면 `auto`, 데이터 절약/2G이면 `none`으로 준비하고 추첨 성공 후 재생 시 로드합니다. `preload`는 브라우저에 대한 힌트이므로 실제 다운로드 양은 브라우저 정책에 따라 달라집니다. 새로운 런타임 패키지는 추가하지 않았습니다.

## 검증

```bash
cd frontend
npm run build
npm run test:mock
npm run dev
```

자동 테스트는 대기 재생/음소거, 탭 숨김·복귀, 추첨·결과·등록 중 재개 방지, 자동 재생 거절, 늦은 응답, StrictMode 정리, 회선별 프리로드와 기존 API·멱등 키·테이블 분리·복구·터치 좌표를 검증합니다.

| 확인 항목 | 이번 환경에서 확인한 범위 |
| --- | --- |
| Chrome 자동 재생 | 데스크톱 Chrome의 `playing` 이벤트와 `data-ready=true`, 실제 머신 영상 표시 확인 |
| Safari 등록·추첨·결과 | 데스크톱 Safari에서 보관통 열기 → 등록 성공 → 대기 화면 → 추첨 영상의 playing → 티켓 상태 확인 |
| 탭 숨김 | Safari에서 document hidden일 때 두 영상 paused 확인; visible 복귀 및 상태별 정지는 자동 테스트로 검증 |
| 반복 연결 | 원본·편집본 첫/끝 프레임 비교, 0.6초 디졸브 적용. 장시간 반복의 주관적 품질은 실기기 추가 확인 필요 |
| 반응형 터치 좌표 | 자동 테스트에서 320/390px 세로, 844px 가로, 1440px 데스크톱의 프레임 비율과 44px 이상 버튼 확인 |
| 오류 대체 | play 거절·늦은 취소는 자동 테스트. 실제 단말의 네트워크 차단·저전력 모드 검증 필요 |

브라우저 조작 도구의 응답 실패로 남은 화면 검증은 완료하지 못했습니다. 실제 iPhone Safari와 Android Chrome은 연결되어 있지 않아 **실기기 검증은 미완료**입니다. 데스크톱 반응형 검사는 단말의 자동 재생 정책 검증을 대신하지 않습니다.

HTTPS 배포 후 두 단말에서 다음을 확인해야 합니다: 첫 접속 자동 재생, 3회 이상 루프, 손잡이/보관통 터치, 질문 등록 후 재개, 연속 터치 시 단일 추첨, 추첨 영상 종료와 티켓, 티켓 닫기, 탭 전환, 회전/주소창 높이 변화, 저전력·데이터 절약, 미디어 URL 로딩 실패 시 포스터/질문 바로 보기. 서버 연동은 기존 계약을 유지했으며 이번 브라우저 확인은 목업 모드입니다.
